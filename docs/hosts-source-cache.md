# Hosts 来源缓存与 DNS 地址持久化

## 两种不同的数据

`dnsaddresses.json` 与在线 hosts 来源缓存不是同一份数据：

- `dnsaddresses.json` 由 resolver 的地址持久化逻辑写入，记录每个 `host:port` 当前可供连接尝试的候选 IP。候选集合可能经过在线 hosts、DNS 查询、内置 seed、旧候选合并和 TCP/TLS 测速排序；文件本身不记录每个 IP 的来源。
- `HostsService` 的映射按域名保存在线 hosts 来源的结果，不包含端口，也不等同于最终连接候选列表。该映射当前只保存在进程内存中。

因此，查看 `dnsaddresses.json` 可以确认程序保留了哪些连接候选，但不能仅凭文件判断某个 IP 是 DoH、在线 hosts 还是内置 seed 提供的。

## 部分来源失败时的缓存规则

配置的在线 hosts 来源并发下载。每个来源单独保留最近一次成功且解析出有效条目的映射：

1. 来源本次成功且解析出有效条目：只替换该来源自己的旧快照。
2. 来源下载失败或解析结果为空：保留该来源上一次成功的快照。
3. 其他来源本次成功：正常更新自己的快照，不影响失败来源的缓存。
4. 最终映射由所有来源的最新有效快照合并，重复 IP 去重。
5. 所有来源本次都失败：不改动当前合并映射，刷新结果标记为失败。
6. 至少一个来源本次成功：刷新结果标记为成功；日志中的 `sources` 表示本次成功来源数，`cached_sources` 表示当前已有有效快照的来源数。

这避免了一个来源超时、另一个来源成功时，成功来源的结果把失败来源独有的域名整个覆盖掉。某个来源恢复成功后，它发布的新快照会替换该来源旧快照，因此该来源已删除的条目也会随之移除。

## 下载超时诊断

在线 hosts 请求仍使用 20 秒的 reqwest 总超时，没有因为诊断改动而延长启动等待上限。日志现在区分三个阶段：

- `stage="response_headers"`：在 `send()` 阶段失败，尚未收到响应头；日志包含该阶段耗时、timeout 和 connect 标记。
- `stage="response_body"`：已收到 HTTP 响应头，但读取 `response.text()` 正文失败；日志包含 HTTP 状态码、响应头耗时、正文读取耗时和总耗时。
- HTTP 状态错误：响应头已收到，但状态码不是成功状态；会记录状态码和响应头耗时。

成功路径的响应头、正文耗时和正文字节数使用 DEBUG 级别记录。正文超时本身使用 WARN 级别，因此正常 INFO 日志级别也能看到它是否卡在正文阶段。

这些指标用于判断下一步是否值得做有限重试：如果一次失败已经消耗接近 20 秒，再立即完整重试会明显增加启动等待；目前不自动重试，也不改变现有超时策略。

## 重启行为与边界

来源快照目前只在内存中维护，不会单独写入磁盘。进程重启后，在线 hosts 来源会重新下载；如果某个来源在启动时失败，它没有可恢复的来源级快照。

但 resolver 的 `dnsaddresses.json` 仍会在启动时加载上次保存的连接候选，DoH/hosts 刷新失败时可按 resolver 的保留逻辑继续使用旧候选。两者提供的是不同层级的容错：

- 来源级缓存：避免同一进程运行期间一次部分失败丢失另一个来源的 hosts 条目。
- endpoint 持久化：避免进程重启后立即丢失上次保存的连接候选。

当前没有给 `dnsaddresses.json` 增加来源字段或时间戳，避免改变现有持久化格式。若后续需要精确追踪 IP 来源，应单独设计向后兼容的记录结构和迁移策略。
